# Adapters

## TL;DR

Every detail is reached through **one small contract declared where it is needed** (core or editor), and fulfilled by **one adapter class** in `src/adapters`. The adapters are: Box2D for physics, PixiJS for drawing, IndexedDB, `localStorage` and Web Locks for storage, the keyboard and pointer for input, the system clock, timers and animation frames for time, workers for test play and import, `fflate` for zips, and the browser for files and the clipboard. Lua (v5) and audio (Later) get a contract and a folder when their version comes. Tests swap every adapter for a fake. v2 adds gradients to the drawing, v3 sensor events and live changes to the physics world and the unstyled shape overlay.

## Physics

```typescript
export type PhysicsEngine = {
    load(): Promise<void>;                          // fetches the wasm once
    createWorld(settings: WorldSettings): PhysicsWorld;
};

export type PhysicsWorld = {
    createBody(definition: BodyDefinition): BodyHandle;            // pose, type, damping, flags
    addSurface(body: BodyHandle, surface: SurfaceDefinition): void; // pieces or chains, density...
    createJoint(definition: JointDefinition): JointHandle;         // two different bodies
    destroyJoint(joint: JointHandle): void;                        // nothing if its body took it
    setGravity(gravity: Point): void;               // m/s²; wakes every body
    step(): void;                                   // 1/60 s
    readMovedBodies(into: BodyPoses): void;         // only bodies that moved this step
    readSensorEvents(into: SensorEvent[]): void;    // v3: the last step's begins, then ends
    contactEvents(): readonly ContactEvent[];       // v4: the last step's begins, then ends
    velocity(body: BodyHandle): BodyVelocity;       // the live px/s and °/s (velocityOf until v4)
    setPose(body: BodyHandle, pose: BodyPose): void;                 // v3: a teleport
    addVelocity(body: BodyHandle, velocity: Point): void;            // v3: adds to the speed, ignoring mass
    setLinearVelocity(body: BodyHandle, velocity: Point): void;      // v4 fix 3: sets the speed, keeping the spin
    setSurfaceSettings(entity: EntityId, settings: SurfaceSettings): void; // v3: Friction and Restitution
    setMotor(joint: JointHandle, motor: HingeMotor): void;          // v3: a Hinge's motor values
    destroyBody(body: BodyHandle): void;
    removeSurfaces(entity: EntityId): void;          // v4: a merged surface destroyed in play
    destroy(): void;
};
```

- **As built in v4 task 13** (standing yes, 2026-11-23): **`removeSurfaces(entity)`** takes every surface the entity gave out of the body it went to, which stays (a shape merged into a group's body, or a surface on the ground); a Dynamic body left with no mass gets its 1 kg back; asking for an entity with no surfaces, or whose body was destroyed, does nothing. `EndOfTickPhase` asks it for every entity a removal takes. *Why: until then only bodies were destroyed, so a destroyed brick on the ground stayed solid in Box2D; v3's only such level destroyed sensor coins, which nothing collides with, so it never showed.*
- **Everything in the definitions is in pixels and degrees.** `Box2dPhysicsWorld` converts to metres and radians with the World's Pixels per metre (a fixed 50 until v4, see [geometry.md](core-model/geometry.md#where-the-scale-lives-v4-fix-12)), and is the only physics code that does.
- It imports `box2d3-wasm/compat` only, see [stack.md](stack.md).
- Handles are the adapter's own numbers, mapped to Box2D ids inside it. Box2D's user data holds the entity id, so contacts (v3) can name entities. **v3:** sensor events name their entities from the adapter's own table instead, because a destroyed shape's end arrives after it can be read (see [triggers-in-play.md](triggers-in-play.md#the-tick-from-v3)).
- It applies the tech notes' Box2D facts: sensors get density 0, a Dynamic body with no mass gets 1 kg, two-sided segments for lines, joints with an empty end attach to a static ground body, the speed cap of 6,000 px/s is Box2D's `maximumLinearSpeed`, and the spin cap of 7.5 turns per second is Box2D 3.2's own 45° a step.
- Contacts and sensor events (v3) are read with Box2D's event arrays after `step()`, so they are delivered after the physics step, never during it.
- **As built in stage 13 step 2** (standing yes, 2026-11-16): the contracts live in `core/physics/contracts/`. A `BodyHandle` is a plain number, the index of the body in creation order. `BodyDefinition` holds the body's entity, its type, position, angle and the BodyComponent's settings. **Gravity stays in m/s²**, in `WorldSettings` and `setGravity`, like the World's Gravity field, and y points down in Box2D too, so nothing flips. `BodyPoses` keeps every body's latest pose by its entity and the list of bodies that moved in the last step; the caller clears that list before each step. One step is 1/60 s in 4 sub-steps, Box2D's recommended count. A Dynamic body gets 1 kg when it is created, until surfaces give it mass (step 3). Rotations are built and read with `DeterministicMath`, not Box2D's approximate `b2MakeRot`. `addSurface` and `createJoint` join the contract with the steps that build them. *Why: the contract only holds what is built and tested, and the [tech notes](../tech-notes.md#physics-and-joints) say why each Box2D detail is handled as it is.*
- **As built in stage 13 step 3** (standing yes, 2026-11-16): `addSurface(body, SurfaceDefinition)` takes one entity's surface: its entity, its pieces in the body's space and the SurfaceComponent's four values. A `SurfacePiece` is a circle with its centre, a convex polygon, or a line, one of `LineChains`' chains, which the adapter adds as one segment per edge. Polygons go through Box2D's `b2ComputeHull`, so their point order doesn't matter, and one whose hull has under 3 points is skipped. After each surface, a Dynamic body left with no mass gets 1 kg again, with no rotational inertia, so it can't spin, as [bodies.md](../requirements/physics/bodies.md) warns. `velocityOf(body)` gives px/s and °/s, for `stateHash` in step 7. `setVelocity` is on `Box2dPhysicsWorld` only, for the tests, until scripts (v5) need it in the contract. **Spin isn't clamped by the game:** Box2D 3.2 holds it to 45° a step, 7.5 turns per second, below the 15 the requirement first said, so the requirement and the motor speed range follow Box2D. *Why: a clamp at 15 could never act, and a lower cap of our own would add a rule Box2D already keeps.*
- **As built in stage 14 step 2** (standing yes, 2026-11-16): a `JointDefinition` is a `HingeDefinition`, a `RopeDefinition` or a `SpringDefinition`. Each holds the joint's entity, `bodyA` (the one that turns) and `bodyB` (the ground body when field B is empty, which the scene builder makes), each end as a level position, and the values play uses, already flipped for a mirrored joint. The Hinge is Box2D's revolute joint with field A as Box2D's body B; each local frame sits on its own end, and B's frame holds the angle between the bodies at the start, from `b2InvMulRot`, so the placed angle reads 0. Resistance is a motor at speed 0 with that strength while Motor is off. `createJoint` refuses one body at both ends; `destroyJoint` on a joint Box2D already destroyed with its body does nothing, checked with `b2Joint_IsValid`. **Box2D 3.2 clamps a Hinge's limits to ±180°**, so Min angle and Max angle now range over half a turn, not a full one, in the requirement and the schema. *Why: a limit past 180° would stop at 180° anyway, so the wider range only promised what can't happen.* A limit is soft: a strong motor pressing on it pushes a few degrees past. The tests are in `Box2dPhysicsWorld.hinge.test.ts`.
- **As built in stage 14 step 3** (standing yes, 2026-11-16): Rope and Spring are Box2D's distance joint with its spring on, their ends set the same way as a Hinge's. A Rope's spring has 0 bounces per second and its limit runs from 0 to Length, with Length also as the rest length; a Spring has Rest length as its length, Stiffness as `hertz`, Damping as `dampingRatio` and no limit. Both take the length play uses, already matched to the drawn gap or scaled. *Why: Box2D 3.2 takes a spring's stiffness in bounces per second, so the mass isn't needed, and a spring of 0 bounces per second pulls nothing until the limit holds.* The tests are in `Box2dPhysicsWorld.distance.test.ts`.
- **As built in v3 task 9** (standing yes, 2026-11-22): **a `SensorEvent` is `{ kind: 'begin' | 'end', sensor, visitor, visitorBody, visitorIsSensor }`**: the sensor's and the visitor's surface entities, the entity of the visitor's body (the World for the ground), and whether the visitor is a sensor too, so `TouchLedger` can leave two sensors out without reading the level. `step()` reads Box2D's sensor events itself, into `SensorShapeTable` (`adapters/box2d/`, `ShapeTable` from v4 task 7), which keys each shape by its index and generation and counts its open overlaps; a destroyed shape's entry is dropped once that count is back to 0. `readSensorEvents` then copies them out, begins first, in Box2D's order. **Every shape gets `enableSensorEvents`**, so every surface is seen. **`setSurfaceSettings` takes the surface's entity**, not a handle, since `PlayValueWriter` changes an entity's values, and changes every surface that entity gave (the World gives one per wall); an entity with no surface in the world (a line play left out) changes nothing. Friction and Restitution change in place and act on contacts already touching; a change of Sensor destroys the surface's shapes and makes them again from the kept `SurfaceDefinition`, and a Dynamic body left with no mass gets its 1 kg back. **`setPose` and `addVelocity` wake the body**; `addVelocity` on a Static body does nothing. **`setMotor` takes a `HingeMotor`** (Motor, Motor speed, Motor strength, Resistance, as in `HingeDefinition`), uses the same motor settings as creating the Hinge, wakes its bodies, does nothing if its body took it, and refuses a Rope or a Spring. `ScriptedWorld` lists every change asked of it and gives the sensor events a test queues after the next step. The tests are in `Box2dPhysicsWorld.sensors.test.ts` and `Box2dPhysicsWorld.changes.test.ts`. *Why: one place counts a destroyed shape's ends, whoever reads them; the flag on the visitor keeps the two-sensor filter in `TouchLedger`, where the architecture puts it, with nothing to look up.*
- **As built in v4 task 7** (standing yes, 2026-11-22): **a `ContactEvent` is `{ kind: 'begin' | 'end', surfaceA, bodyA, surfaceB, bodyB }`**: the two solid surfaces' own entities and the entities of their bodies (the World for the ground), in Box2D's order, not by which one moved, so `ContactLedger` must look at both sides. **`SensorShapeTable` became `ShapeTable`**, which names contact events the same way and counts a shape's open sensor overlaps and contacts together, so a destroyed shape's entry stays until both kinds of end are in. `step()` reads both kinds of event; `contactEvents()` returns a copy of the last step's, begins first. **The surfaces that send contact events are `WorldSettings.contactEventSurfaces`**, a set of surface entities, none when left out; `PhysicsSceneBuilder.build` takes it as an optional fourth argument, for `TriggerIndex` (task 8) to fill. Each shape's `enableContactEvents` is set when it is made from that set, so a surface rebuilt by a change of Sensor gets its switch again. **`velocityOf` was renamed `velocity`**, as the v4 architecture names it. `ScriptedWorld` gives the contact events a test queues after the next step, as it does sensor events, and `ScriptedEngine` keeps the `WorldSettings` it was given. The tests are in `Box2dPhysicsWorld.contacts.test.ts`. *Why: the set is known when the run starts, since triggers can't be added in play, and putting it in the world's settings lets one place set every shape's switch, a rebuilt one included; the body entities come with the surfaces because `ContactLedger` filters out parts of one group and needs no lookup for it.*
- **The tech notes' physics facts were written for Box2D v2.4.** The plan's physics stage rechecks each one against v3.2 and writes the result into the tech notes.

## Rendering

`PixiLevelView` (`adapters/pixi/`) owns a PixiJS renderer and its stage, without an `Application`, and draws a given `Level`: the editor's, or the `PlayMirror` during play.

| Class | Job |
|---|---|
| `PixiLevelView` | Creates the canvas on `mount`, follows the host's size and `devicePixelRatio`, decides when to draw |
| `LevelDisplay` | One `EntityNode` per entity, nested like the entity tree, so children follow parents and the draw order comes from the tree |
| `EntityNode` | A PixiJS `Container` for the entity (its matrix, its hidden state) and one `Graphics` for what it draws |
| `EntityDrawing` | Builds the `Graphics` content from the ShapeComponent's outlines or the PathComponent, and the StyleComponent. Rebuilt only when one of them changes. Its fill comes from `PixiFill` (v2) |
| `PixiFill`, `GradientTextures` (v2) | A `Fill` as what `Graphics.fill` takes, and the shared gradients behind it: see [gradients](#gradients-v2) |
| `overlays/` | `grid/` holds `GridOverlay`, `bounds/` holds `BoundsOverlay` (the level bounds' edge and **World** label), `selection/` holds `SelectionOverlay` with `planSelection` and `SelectionSource` (outlines, handles, the selection box, the readout), `drawing/` holds `DrawingPreviewOverlay` with `planDrawing` (the Shape tool's preview, stage 10, and from v2 the pen's through `planPen` and `drawPenPlan` and the Pencil's through `drawPencilStroke`), `gradient/` holds `GradientHandleOverlay` with `planGradientHandles` (v2). `letterbox/` holds `LetterboxOverlay`, Fixed size's black bars over everything during play (stage 15). Beside them: `CameraFrameOverlay`, `JointIconOverlay`, `PhysicsViewOverlay`, and what several share: `FrameLabel`, `levelBackground` and `overlayLook` (the accent, the overlays' font, the handle) |

- **Drawing only when something changed.** There is no PixiJS ticker: no `Application` is made. A dirty flag set by level updates, the selection, the tools' previews, `ViewState` and the play session's frames triggers one render on the next animation frame. An idle editor draws nothing.
- **Drawing order:** the level (back to front), then the grid, then the editor overlays. Overlays live in a container with no zoom, so handles, icons and outlines keep their size on screen.
- **Each entity draws one thing**, text before path before shape, as the requirement says. A shape with no StyleComponent is drawn as a thin outline in the editor and not at all in play.
- **The physics view** draws the collision pieces from `PiecesCache` at each entity's level matrix, in the editor and in play alike (owner, 2026-11-13).
- **During play** the view follows the camera from the tick reports: Fixed size scales the camera's box to fit the window, centred, with black bars. Editor-only drawing (handles, the camera frame) is hidden unless a View menu switch shows it. **Joint icons are never drawn in play**, whatever their switch, so an unstyled joint is invisible like any entity, and they come back after Stop (owner, 2026-11-17).
- **Sharp at any browser zoom:** the renderer's resolution follows `devicePixelRatio` and a `ResizeObserver` on the host, as the tech notes say. Antialiasing is on.
- Culling and batching are described in [performance.md](performance.md).

### The minimap

`MinimapView` (`adapters/pixi/minimap/`) draws the [minimap](../requirements/editor/workspace.md#the-minimap--v1): the whole level bounds, fitted and centred in the island, each entity's fill without outlines, and an accent rectangle for what the level view shows. Built in stage 19 step 13 (standing yes, 2026-11-18).

| Part | Job |
|---|---|
| `MinimapView` | The canvas, the host's size, and when to paint |
| `paintEntityFill` | One entity's fill on a 2D canvas: a shape's filled outlines and circle, or a closed path |
| `minimapFit`, `viewRectangle` | Plain sums: where the level bounds sit in the picture, and where the view's rectangle sits on them |

- **A plain 2D canvas, not a second PixiJS renderer.** *Why: a second renderer means a second WebGL context and a second `Graphics` for every entity, while the minimap is 174 × 87 px and draws fills only.* It stays in `adapters/pixi` because it shares `tracePath` and the colour reading with `EntityDrawing`.
- **It never works inside the level view's frame.** It runs on `Timer`, not `FrameScheduler`. *Why: dragging 1,000 of 10,000 entities already takes about 15 ms of a frame's 16.7.*
- **Painting is cut into slices** of 100 entities, 16 ms apart, on a canvas nobody sees. When the last slice is done that picture replaces the shown one, so a half-painted level never shows. A level of 100 entities or fewer paints at once; one of 10,000 takes about 1.6 s. Each slice ends by reading one pixel, on a canvas kept on the CPU. *Why: the browser otherwise saves up every fill and plays them back when the picture is first used, 4 to 6 ms at 10,000 entities, enough to drop a frame.*
- **At most four updates a second:** a change waits 250 ms, and every change in that time joins the same update. A change during painting waits for the painting to end. An idle editor runs nothing.
- **The view's rectangle** is drawn over the finished picture, so moving the view repaints no entity. It is at least 4 px wide and tall, so it stays visible at high zoom, and it is left out when the view shows none of the level.
- **Painting skips** hidden entities, lines, unfilled shapes and shapes with no StyleComponent, and an entity removed while the painting runs.
- **The draw order is kept between paintings** until an entity is added, removed or moved in the tree. *Why: listing 10,000 entities takes about 2 ms, and a drag changes no order.*
- **The island is 180 × 93 px**, so the picture inside its 3 px edge is 174 × 87, the 2:1 of a new level. **Level bounds of another shape** leave bars of the app's colour beside them: the island keeps its size, because the Entities viewer's height is worked out from it.

### Stage 4's choices

Made under the standing yes (2026-11-14), before building, and the "as built" entries while building (2026-11-14 and 15). The [plan](../steps/stage-04.md) has the steps.

- **Stage 4 builds what later stages call, not their inputs.** The wheel, Space and middle-drag panning come with `PointerInput` (stage 9); F and the Zoom menu are commands (stages 5 and 6); the `Back to level` button is ui (stage 6, moved to stage 9 with panning: see [ui.md](ui.md#stage-6s-choices)); remembering the view in the browser is `LocalStorageSettings` (stage 12); `SelectionOverlay` is stage 9's and `DrawingPreviewOverlay` stage 10's. *Why: a stage never builds what a later stage owns.*
- **`PixiLevelView` is given the level, its caches, `ViewState`, `ViewSettings` and a `FrameScheduler`**, not the `EditorSession`, which stage 5 builds. `show(level, caches)` swaps the level, for New, Import and the `PlayMirror`.
- **`ViewState` holds the level position at the middle of the view, the zoom and the view's size** in CSS pixels, which `PixiLevelView` sets on each resize. Zoom 1 is 100%: one level pixel per CSS pixel; the renderer's resolution covers `devicePixelRatio`. *Why: keeping the middle means resizing the window keeps the level where it was.*
- **Fitting a rectangle** (F, the whole level, the camera frame) zooms so it fills the view less 40 screen px on each side, within 1% to 1000%, and centres it. Nothing to fit leaves the view alone.
- **`ViewState` as built** (`editor/view`, standing yes, 2026-11-14): `levelToScreen`, `screenToLevel` and `matrix()` convert positions; `panBy` takes screen pixels; `zoomAt(screenPoint, zoom)` keeps the point under the mouse still; `zoomIn` and `zoomOut` double and halve the zoom about the middle (*proposal*: the steps the wheel uses come with `PointerInput` in stage 9); `fit(bounds)` fits a rectangle, and one with no width or height fits along its other side, so a single point zooms to 1000%; `setPanLimit(worldRectangle)` sets the pan limit and pulls the middle inside it; `holdsNothing(contents)` says when `Back to level` is due. Its `version` moves only on a real change.
- **`ViewSettings` as built:** the four View menu switches, `grid`, `jointIcons`, `cameraFrame` and `physicsView`, with `isOn`, `set` and `toggle`. A new editor starts with the physics view off and the other three on (*proposal*), because the physics view draws over everything. Folded cards join it with the Entity inspector in stage 8.
- **`PixiLevelView` as built** (`adapters/pixi`, standing yes, 2026-11-14): `PixiLevelView.create(parts)` is async, because PixiJS starts its renderer asynchronously, so `mount(host)` stays a plain call that only places the canvas. It makes a renderer with `autoDetectRenderer`, not an `Application`, so there is no ticker to switch off. *Why: an `Application` only adds the ticker and a resize plugin, and the view does both itself.* It asks for WebGL, then the canvas renderer, and skips WebGPU (*proposal*). *Why: WebGL works in all three browsers the tests run, so one path is tested.* `markDirty()` asks the `FrameScheduler` for one frame, and changes before it draw once. The resolution comes from a `PixelRatioSource`, which `DevicePixelRatio` in `adapters/browser` fulfils with a media query on the current ratio, so browser zoom and a move to another screen are seen. The level sits in a layer that takes `ViewState.matrix()`; the overlays will sit beside it, unzoomed. `renderCount` counts draws for the tests.
- **`LevelDisplay`, `EntityNode` and `EntityDrawing` as built** (`adapters/pixi`, standing yes, 2026-11-14): `PixiLevelView.show(level, caches)` makes a `LevelDisplay`, which builds one `EntityNode` per entity and follows `LevelSignals.updated`. An `EntityNode` is a `Container` with the entity's own matrix (from its TransformComponent, so PixiJS multiplies the parents'), `visible` from its own eye, a layer for its children's nodes with the top row last, and one `Graphics`. **An entity draws in front of its children, and the World behind them**, because the draw order is the panel order backwards with the World first. *Why: that is what `Level.entitiesInDrawOrder` says.* A TransformComponent change sets only the matrix; a ShapeComponent, PathComponent or StyleComponent change marks the drawing, and the marked drawings are rebuilt just before the next render, so a drag that changes a style many times between frames rebuilds once. Opacity is the `Graphics`' alpha, so it doesn't fade the children. Outlines get **round caps** as well as round joins, so a line's ends stay within half its width too, as `BoundsCache` counts. Whether a shape without a StyleComponent shows its thin line is an `EntityDrawingOptions` given to `PixiLevelView`: on in the editor, off in play. Until stage 5's `DerivedCaches`, the display is given only `PiecesCache` and `BoundsCache` (`LevelDisplayCaches`). `drawingBuildCount` counts rebuilt drawings for the tests. **Scale outline off** (stage 18 step 7, standing yes, 2026-11-17): PixiJS can't keep a stroke's width under its container's scale, so `EntityDrawing` traces every point moved by the entity's own scale and skew and sets the `Graphics`' matrix to their inverse: the shape lands where it would, and only the stroke is unstretched. A stretched circle is traced as points, about one every 4 px of its edge, at least 32, because a skewed ellipse can't be drawn with Pixi's own. `EntityNode.drawnOutlineStretch` remembers the stretch a drawing was built with, so a TransformComponent change rebuilds the drawing only when the scale or skew changed, never for a move or a turn.
- **Culling as built** (`adapters/pixi`, standing yes, 2026-11-14): every render, after rebuilding marked drawings, `LevelDisplay.cull(area)` walks the tree from the World. A node whose subtree bounds miss the area gets `renderable = false` and its subtree isn't visited; otherwise its `Graphics` is `renderable` only when its own bounds meet the area. Hidden subtrees aren't visited, since showing one is a change that renders and culls again. `PixiLevelView` grows `ViewState.visibleBounds()` by 2 screen px, so the 1 px line of an unstyled shape, which `BoundsCache` doesn't count, isn't cut at the edge. *Why: culling every render needs no tracking of what moved, and with the caches warm it costs one bounds check per node that is on screen or next to it.* **Changed in stage 9** (standing yes, 2026-11-16): while the visible area stays the same, only the entities whose components changed are culled again, with their subtrees and parents; see [performance.md](performance.md#targets-and-their-tests). *Why: walking 10,000 entities took 4 ms of a drag frame's 16.7.*
- **The grid, bounds and camera frame overlays as built** (`adapters/pixi/overlays`, standing yes, 2026-11-14): they sit in front of the level layer, unzoomed, and draw in screen pixels, so they keep their size at any zoom. Every render redraws them, after culling, like culling itself. **The grid is drawn over the level** (*proposal*). *Why: the World's fill, drawn first inside the level layer, is the background, so the grid can't sit between it and the entities without splitting the World's drawing; at 7% to 32% the lines stay faint over shapes.* `GridPlan` works out the lines: the step is the grid size, **times five as often as needed to keep lines 8 screen px apart** (`gridStepAt` in `editor/view/gridSpacing.ts`, which `GridSnapper` shares). *Since 2026-11-22 (owner) there are no fainter lines between steps.* *Why: the requirement says lines fade when too close; dropping to every fifth line keeps the count bounded by the view's size at 1% zoom.* So the fainter lines were every 10 px for the 50 px grid, then the default, and a fifth of any other size. Lines are counted from the origin as whole numbers, and sit on the middle of a screen pixel. A World with no fill shows the app's dark colour behind the canvas, so it counts as a dark background. **Since the redesign (stage 19 step 14) the grid is drawn only inside the level bounds, and nothing is drawn outside them:** the canvas stays clear there, so the app's `--app` colour shows, and an entity placed outside stays visible. *Why not paint the outside: an opaque rectangle over the level would hide those entities, and they can still be selected and moved.* **`BoundsOverlay` has no switch:** the View menu has none for it. It draws the 1 px edge and the `FrameLabel` **World** and the size. The level bounds come from `levelBoundsOf(level)` in `core/derived`, the World's rectangle centred on the origin, which `ViewState`'s pan limit and fitting the whole level will use too. **`CameraFrameOverlay` hides with the camera's eye** (and the World's), and reads the frame from `BoundsCache`; its `FrameLabel`, shared with the bounds, is two PixiJS `Text`s in JetBrains Mono, drawn white and tinted, so only a new size draws text again. The frame follows the World's fill; the label follows what it starts on, so a label above the level bounds is light. `PixiLevelView` also listens to the shown level's `levelVersion`, so a new grid size or camera size draws again, and to `ViewSettings`. `overlays` exposes the three for tests.
- **The joint icons and the physics view as built** (`adapters/pixi/overlays`, standing yes, 2026-11-14): both sit over the other overlays, unzoomed, and redraw every render; the icons are on top so a joint stays clickable over the physics view. **A joint's own bounds** in `BoundsCache` are the point at its position, joined with its path's bounds for a Rope or Spring, so the drawn path isn't culled. `JointIconOverlay` reads each joint's position from the `WorldMatrixCache`, skips joints off screen, and **hides an icon with the joint's eye or a hidden parent's** (*proposal*). *Why: a hidden entity draws nothing in the editor; the joint still works in play.* `PhysicsViewOverlay` draws **every entity with a ShapeComponent and a SurfaceComponent**, hidden or see-through, because a surface with no body is Static and still collides. It draws the cached pieces at the entity's level matrix in screen pixels; a circle on a matrix that scales unevenly or skews is drawn as its 32-point polygon, as the play copy gives it to Box2D; a line draws its `LineChains`; **with Walls on, the World's rectangle draws its four edges** (*proposal*). Shapes whose own bounds miss the view are left out. So `LevelDisplayCaches` now holds the `WorldMatrixCache` too, and the overlays get all three caches.
- **The page's wiring as built** (`app`, standing yes, 2026-11-15): `main.tsx` keeps the React heading and calls `startLevelView(host, level)`, which builds `ViewState` with the level's pan limit, `ViewSettings`, `AnimationFrames`, `DevicePixelRatio`, the three caches and a `PixiLevelView`, then mounts it in `#level-view` and shows the level at 100% on the origin. The level is `buildTestLevel()` in `app/testLevel.ts`: a square in a colour nothing else uses, an ellipse, a see-through one-stroke star, a turned group's bar and a shape with no StyleComponent. *Why: stage 5's `EditorSession` owns the level, its caches and the view, so stage 4 adds only what draws one; both files go when the editor page replaces them.* *Both went in stage 6 step 7, replaced by `app/EditorComposition.ts` and the `EditorShell`; see [ui.md](ui.md#stage-6s-choices).* The Playwright test reads colours from a screenshot of the canvas, decoded in the page, because a WebGL canvas can't be read back after it is shown, and samples off the grid's lines.
- **The time contracts as built** (`editor/time`): `FrameScheduler`, `Clock`, `Timer` and `Cancel`, with `ManualFrames`, `ManualClock` and `ManualTimer` in `editor/time/testing`. `Clock` and `Timer` came in stage 5 with `StatusText`. **A `ManualTimer` moves its own `ManualClock`**, which a test can hand to the code under test too, so a `Clock` and a `Timer` read the same fake time; `advance` runs each callback due at its own time, earliest first, and two due at once in the order they were asked for (standing yes, 2026-11-15). *Why: history joining and autosave read both, and their tests need one time.*
- **The pan limit:** the view's middle stays inside the World's rectangle grown on every side by its larger side. **The view holds nothing** when it doesn't overlap the World's subtree bounds. *Why: "well outside the level" with one rule that scales with the level.*
- **Shapes are filled from the polygon pipeline's filled outlines**, the same `PiecesCache` result physics uses, and their outline is drawn along the shape's own points, with round joins. So a self-crossing polygon fills as it collides. *Why: collision always matches what you see.* Paths are drawn as PixiJS curves.
- **A circle is drawn as a true circle**, stretched by its node's matrix, so a circle scaled unevenly shows as a smooth ellipse in the editor, while the physics view shows the 32-point polygon it collides with (standing yes, 2026-11-15). *Why: a drawing is built in the entity's own space and rebuilt only when its ShapeComponent or StyleComponent changes; drawing the 32 points would make it depend on every parent's TransformComponent too. The two differ by under 0.5% of the radius.*
- **A shape with no StyleComponent** is drawn in the editor as a 1 screen px line, `#1D2430` at 60% (*proposal*), with PixiJS's `pixelLine`, so it stays thin at any zoom.
- **Hiding** sets the `EntityNode`'s `visible`, and PixiJS hides its children with it, which is what `HiddenCache` says. The World is drawn like any entity, first, so its fill is the background.
- **A joint's own bounds are the single point at its position.** Hit testing and F add the icon's 7 screen px around it at the current zoom. *Why: the icon keeps its size on screen, so its size in level pixels depends on the zoom, which `BoundsCache` doesn't know.*
- **Joint icons** sit at the joint's position: Hinge is the design's circle with a dot, Rope the circle with a short upright line, Spring the circle with a small zigzag (*proposal*).
- **The grid's dark background** is one whose brightness, 0.299 R + 0.587 G + 0.114 B, is under half, as [the level view's colours](../design/level-view.md) say.

## Storage

| Adapter | Uses | Notes |
|---|---|---|
| `IndexedDbLevelStore` | `idb` on IndexedDB database `engine-v3`, store `level` | One record, written in one transaction with `durability: 'strict'`. All or nothing |
| `LocalStorageSettings` | `localStorage`, key `engine-v3/settings` | Small editor settings, read before the first draw. Every read and write is wrapped, and a failure falls back to defaults |
| `WebLockTabGuard` | `navigator.locks.request('engine-v3/level', ...)` and a `BroadcastChannel` of the same name | Held for the page's life. A tab finding it held asks on the channel; the holder hands over (saves, turns read-only) and lets go. Not let go within 3 s, it is stolen (`steal: true`) |
| `BrowserPersistence` | `navigator.storage.persist()` | Asked once, after the first successful save |

Details of what is saved and when are in [persistence.md](persistence.md). Storage errors become `SaveState` failures, never silent, see [errors.md](errors.md).

## Input

- **`KeyboardInput`** listens on the window in the capture phase, not passive. It builds a `KeyboardInputData` (code, key, modifiers, AltGr state, repeat), asks `ShortcutDispatcher`, and stops the browser's default only when the editor used the key. It reads which part of the page has focus (`FocusPlace`) from the focused element when the key goes down, and whether the mouse is over the level view from `pointerover`. On the window's `blur` it releases every held key. *As built (stage 6, step 5, standing yes, 2026-11-15):* reading `document.activeElement` at key down replaces tracking `focusin`, because it can't fall out of step with the page. An element's own blur also reaches the capturing listener, so only a blur whose target is the window releases the keys. The held keys are kept (`isHeld(code)`) for the tools of stage 9; nothing reads them yet.
- **`PointerInput`** listens on the canvas, converts positions with `ViewState`, captures the pointer during a drag, cancels a drag when the window loses focus, and turns the wheel into zoom (Ctrl+wheel too, for pinch) and Shift+wheel into a sideways pan. It stops the middle button's autoscroll. *As built (stage 9, step 12):* see [selection-and-tools.md](editor/selection-and-tools.md#stage-9s-choices); `KeyboardInput` passes key ups to the dispatcher from then on.
- **No page gestures:** `overscroll-behavior: none` and `touch-action: none` on the editor page, as the workspace's small features ask.
- **During play** (v3), `HeldKeys` also keeps the keys pressed since the last batch, which `PlaySession` sends with it, so a press shorter than a tick counts. `KeyboardInput` is given `PlaySession` as its `GameKeys` and stops a key's default when the editor used it or the level uses it (`usesKey`), so Space and the arrows don't scroll; see [triggers-in-play.md](triggers-in-play.md#keys-during-play).

## Time

```typescript
export type Clock = { nowMs(): number };
export type Timer = { after(delayMs: number, callback: () => void): Cancel };
export type FrameScheduler = { nextFrame(callback: (timeMs: number) => void): Cancel };
```

The editor never calls `Date.now`, `setTimeout` or `requestAnimationFrame` itself. History joining, the 4-second status text, autosave's 2 and 20 seconds, the pacer and the watchdog all take these contracts, so their tests run on fake time.

## Workers

- `WorkerGameRunner` and `GameWorkerHost` are the two ends of the game worker. `app/workers/game.worker.ts` builds the host with the real `Box2dPhysicsEngine`, and `app/createGameWorker.ts` starts it. `EditorComposition` prepares one `WorkerGameRunner` when the editor opens. `DirectGameRunner`, its fake, is in `editor/play/testing/` (standing yes, 2026-11-16).
- `ImportWorkerClient` and `ImportWorkerHost` are the two ends of the import worker, which unzips and checks a file away from the page, as the tech notes advise. `app/workers/import.worker.ts` builds it.
- Each protocol is plain data types beside its two ends, in `adapters/worker/import/` and `adapters/worker/game/` (standing yes, 2026-11-16). Large arrays are transferred, not copied.

## Lua (v5) and audio (Later)

- **Lua:** `WasmoonScriptEngine` fulfils core's `ScriptEngine`: compile a file once, run it once per entity with a fresh environment, call handlers, and stop a script on an error. It also runs in a second, throwaway worker in the editor to check syntax and read a script's `variables` table, as the tech notes advise. The safe library rules (no `io`, `os`, `load`, frozen library tables, no `__gc` or `__mode`) live in that adapter.
- **Audio:** `WebAudioSoundPlayer` fulfils core's `SoundPlayer`. Whether a sound is still playing is worked out by the simulation from ticks and the file's length, never asked from the real audio, as the tech notes require.

### Gradients (v2)

- **`PixiFill`** turns a `Fill` into what `Graphics.fill` takes: a colour, or a PixiJS `FillGradient`, linear or radial (inner radius 0 at the centre). **It uses `textureSpace: 'global'` with a matrix from `fillBoxOf`'s box** (v2 task 3, standing yes, 2026-11-21). *Why not `local`, the plan's first pick: a browser test reading pixels showed `local` restarts on each traced shape and mirrors some linear directions; see [tech-notes.md](../tech-notes.md).* The gradient still turns, scales and resizes with the entity, since the box is in its own space, and a radial gradient in a box that isn't square is an ellipse.
- **`GradientTextures` shares one `FillGradient` between gradients of the same kind and stops**, counted, and destroys it when its last entity lets go. *Why: each `FillGradient` makes a texture, and 10,000 copied platforms with one gradient would otherwise hold 10,000.*
- The play mirror draws through the same `EntityDrawing`, so gradients play as they show, and a fill changed during play rebuilds the drawing as before.
- **`GradientHandleOverlay`** draws the [gradient handles](editor/selection-and-tools.md#gradient-handles-v2) over the selection overlay: the line or the radial gradient's dashed circle (an ellipse when the box isn't square), the end dots in the gradient's colour at 0% and 100%, and stops strictly between as small dots. `planGradientHandles` is tested in Node, as `planSelection` is.

### The unstyled shape overlay (v3)

- **`UnstyledShapeOverlay`** (`adapters/pixi/overlays/unstyled/`) draws any shape with no StyleComponent, such as a trigger the [Trigger tool](editor/drawing-and-points.md#the-trigger-tool-v3) made, as a dashed edge, so it can be seen (v3 task 8, standing yes, 2026-11-22). Only a shape with a TriggerComponent gets the bolt (owner, 2026-11-27: an invisible ground piece under painted children looked like a trigger). It sits over the grid and under the selection, and hides in play with the other editor-only drawing. The level itself no longer draws an unstyled shape's thin line, only an unstyled path's. The bolt is a filled polygon on the outline's centroid on screen, upright at any rotation, 0.9 times the outline's inradius on screen tall (twice its area over its perimeter, so a long thin trigger's bolt fits its short side), and left out under 10 px and on a line (standing yes, 2026-11-22, after the owner asked for it to scale with the zoom).
- **As built in v4 fix 3** (2026-11-23): **a `SensorEvent` also names `sensorBody`**, the entity of the sensor's body, so `TouchLedger` can name the sensor's side as `other` for a solid visitor's touch trigger. **`SurfaceSettings` lost `sensor`**, since the SurfaceComponent did: `setSurfaceSettings` changes Friction and Restitution in place and never rebuilds a surface. `SurfaceDefinition.sensor` stays, set by `PhysicsSceneBuilder` for a pass-through shape under a touch trigger ([triggers-in-play.md](triggers-in-play.md#the-tick-from-v3)). **`setLinearVelocity(body, v)`** joins the contract for Change value's Set on Body › Velocity, waking the body; a Static body doesn't move. `WorldSettings.contactEventSurfaces` is filled from `TriggerIndex.touchSurfaces().contactEvents`, the solid shapes under a touch trigger.
