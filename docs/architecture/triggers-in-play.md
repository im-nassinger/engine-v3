# Triggers in test play

## TL;DR

**How triggers run in the game worker**, built in v3 and v4, moved here from [v3's architecture](../versions/v3/architecture.md) when v3 closed (2026-11-22) and from [v4's](../versions/v4/architecture.md) when v4 closed (2026-11-23). Three tick phases join v1's: **`EventPhase`** lists the tick's events in a fixed order after the physics step, **`TriggerPhase`** runs the triggers that hear them, in Entities viewer order, and **`EndOfTickPhase`** removes what was destroyed and ends the run on Win or Lose. Every changed value goes through **`PlayValueWriter`**, which tells the physics world when it owns the value. The tick report gains **changed values, the run's end and play warnings**, which the page shows; **Restart** builds a new run from the `LevelData` the worker kept. v4 adds **contact events** from Box2D, **variable changes and custom events**, heard in the same tick, **waiting runs** for Wait, and component values in the check. **Fix 3** (2026-11-23) makes touching one event for solid and pass-through shapes, counted by one `TouchLedger` from both kinds of Box2D report, builds a sensor for a shape with no Surface under a touch trigger, merges the checks into one value check, and drops "no entity with this tag is left", Destroyed and Push. The trigger model itself is in [core-model/triggers.md](core-model/triggers.md); the rest of test play in [simulation.md](simulation.md).

## The tick, from v3

| Phase | Does |
|---|---|
| `InputPhase` | Builds `InputState` for the tick: each key and each input pressed, released or held |
| `PhysicsPhase` | One step, then reads the moved bodies, and **the sensor events and the contact begin and end events** into `TouchLedger` (`PlayTriggers.readTouches`) |
| `JointPathPhase` | As in v1 |
| **`EventPhase`** | Lists the tick's events, in a fixed order: level start (first tick only), keys and inputs, timers, waiting runs due this tick (v4), touched, no longer touched |
| **`TriggerPhase`** | For each event in that order, the triggers that hear it, decided once, in Entities viewer order; their checks, then their actions. Its rounds also carry (v4) variable changes and custom events, which actions set off |
| `LevelBoundsPhase`, `CameraPhase` | As in v1. `CameraSettings` reads Follow and Smoothing each tick |
| `EndOfTickPhase` | Removes destroyed and marked entities (and, from v4, cancels their waiting runs), ends the run on Win or Lose, writes the report |

The events' bookkeeping is in `core/simulation/triggers/`, the actions in `core/simulation/actions/`, the inputs in `core/simulation/inputs/`, the run's end (`RunEnd`, `RunEnding`) in `core/simulation/end/` (standing yes, 2026-11-22).

- **Events come after the physics step**, so touches are the step's own, and a change of Body › Velocity lands in the next step, 1/60 s later. *Why one place: every event in a tick is seen in one order, which is what the determinism test can check.*
- **`TouchLedger` counts per trigger owner and touching entity**, not per pair of shapes: "touched" fires when a count goes from 0 to 1, "no longer touched" when it goes back to 0. **Sensor events and contact events count the same way, both ways round** (fix 3): the owners of a shape are its entity and every group above it with a touch trigger, and the touching entity is the other shape's body entity, or that shape's own entity when it is on the ground, so a ball touching a floor with no body names the floor, not the World. A solid player walking into a pass-through coin is touched by the coin too. Two sensors are filtered out here, and so are parts of one owner touching each other. The counting is `OwnerCounts`. *Why one ledger: one event, so a bump and an overlap with one entity are one touch, and stop only when both end.* An end event Box2D sends when a body is destroyed outside the step waits for the next tick. **A count is compared before and after all of a step's events**, so a surface rebuilt in the step fires nothing (standing yes, 2026-11-22). *Why: Box2D 3.2 sends the old shape's ends and the new one's begins in the same step (`box2dFacts.test.ts`).*
- **The adapter names a sensor event's two entities from its own table**, `SensorShapeTable` (`ShapeTable` from v4, which names contact events too), not from Box2D's user data ([adapters.md](adapters.md#physics)). *Why: in 3.2 a destroyed shape's end arrives with the next step, when the shape can no longer be read ([tech notes](../tech-notes.md#triggers)).*
- **`InputState`** reads, per tick, the keys held and the keys pressed since the last batch, which `HeldKeys` keeps, so a press shorter than a tick still counts. `TickInputs` carries `pressedKeys` on a batch's first tick only. A key is down while held or pressed this tick; an input is held while any of its keys is, and pressed when one of its keys is and none stayed held through. `PlayRun.inputs` holds the run's `PlayInputs`, which `InputPhase` moves on each tick. An unknown input name reads as not held and goes to `PlayInputs.unknownInputs`, once each, as a play warning.
- **`TriggerTimers`** count whole ticks: "after 60 s" is tick 3,600 after the trigger was switched on, and a timer on from the start counts from tick 0. Anything that slows the ticks slows the timers too.
- **`TriggerPhase` runs rounds:** the listed firings, then the firings their actions set off (`ChainedEvents`), such as a Change value of a variable another trigger watches, heard in the same tick. After 32 rounds the rest are dropped with one play warning (the chain limit). **A fresh firing asks again for on/off and is dropped when its trigger is off by the time it is reached** (fix 4), so two touches of a resting spike in one tick hurt once; then `RunnableTriggers` (each trigger's `triggerProblems`, worked out once), then the checks. **A resumed run doesn't ask for on/off** (fix 4), so a run that switched its own trigger off to rest goes on after its Wait and can switch it on again; it asks `WaitingRuns.stillResumes` instead (below). A level start trigger switched on during the first tick hears level start.
- **`TriggerIndex`** lists, at the start of a run, the triggers that hear each kind of When, in Entities viewer order, and keeps it when entities are destroyed. Touch triggers are found from the touched shape's entity.
- **What physics builds for touching** (fix 3): `TriggerIndex.touchSurfaces()` gives, for each entity with a shape whose entity or a group above it has a touch trigger, **`contactEvents`** when it has a SurfaceComponent and **`sensors`** when it has none. `startSimulation` reads it from the read level before its physics is built (through `startPlayCopy`), and `PhysicsSceneBuilder` builds each sensor where a surface would go (`BodyMembership.shapeTargetOf`: its body, or the ground; a line on a Dynamic body is left out), with the SurfaceComponent's defaults and no weight. A shape with no Surface and no touch trigger stays out of physics. *Why sensors inside the engine: Box2D only reports a hit between solid shapes while it pushes them apart, so noticing without pushing needs a sensor; the pre-solve callback could cancel the push, but it would call into JavaScript for every touching pair every tick. Why contact events only where needed: Box2D reports every begin it is asked for, and a level of 10,000 bodies with one touch trigger must not pay for 10,000. Triggers can't be added during play, so the sets are known when the run starts.* Box2D's facts are in the [tech notes](../tech-notes.md#physics-and-joints), the contract's calls in [adapters.md](adapters.md#physics). *Why: a level of 10,000 entities must not walk every trigger every tick.*

## The events v4 added

- **Variable changes:** `PlayValueWriter` tells `VariableWatch` of every variable it writes, one by one, with the old value and the new; a write that changes nothing is ignored. "A variable changes" fires when the value differs; with "becomes", when the condition was false before and is true now. The If check and "becomes" compare with one rule, `variableMatches`, under which values of two types never match. A level's variable is heard by every trigger with that When; an own variable only by the triggers of the entity holding it; a World trigger naming a World variable as its own hears it as the level's. `TriggerIndex` keeps the level's by name and the own ones by entity.
- **Custom events:** Fire custom event adds one event per hearer, with `other` as the firing trigger's `this`. The hearers are each target and everything inside it (`entitiesIn`, parents first, top row first), each once per Fire; a group above the target doesn't hear it (owner: 2026-11-23). `TriggerIndex` keeps the custom triggers by name, then by entity, so a name nobody hears costs nothing.
- **Chained events stay within the 32 rounds**, so a custom event that fires itself stops at the chain limit.

## Waiting runs

- **`ActionRunner` runs a trigger's actions until a Wait, then hands `WaitingRuns` the rest:** the trigger, `this`, `other`, the next action's index and the tick it is due (now plus the seconds in whole ticks, at least one tick). A resumed run is a `TriggerFiring` with `resumesAt`, run from that action by `TriggerPhase`, and **doesn't ask its checks again**. *Why no recheck: "wait 2 s, then close" must close, whatever happened meanwhile.*
- **Due runs go** in order of due tick, then trigger order, then the order they started, after timers in `EventPhase`. Two firings during one wait both run.
- **A trigger holds at most 32.** The 33rd firing is dropped at its Wait, after the actions before it ran, with the play warning `tooManyWaitingRuns`, once per run.
- **Setting a trigger's *Enabled* to false** cancels its runs (`PlayValueWriter`), **even when it is already off** (fix 4), so a resting trigger switched off by another trigger stays off; the run doing the switching isn't waiting, so it goes on. Removing its entity cancels them too (`PlayTriggers.removing`). **A cancel also reaches the runs `takeDue` gave this tick and not yet run** (`stillResumes`), so one due in the tick another trigger switches it off, earlier in that tick, is dropped. Restart starts empty.

## Actions

- **`ActionRunner`** finds the targets (`targetsOf`: `this`, `other`, the named entity, or every entity tagged, in Entities viewer order) and runs each action on each, skipping a target that lacks what the action needs.
- **The value check (`checksPass`)** reads its value on each target and is true when one passes; with no target it is false. A level's variable is read on the World whatever the target. A tag reads as held when the target or a group above it has it, so "has" (is) and "doesn't have" (isNot) compare it like a string. Variables and tags compare with `variableMatches`.
- **Change value goes through `PlayValueWriter`**, which writes only what `changeableValues` offers the entity, with the field type's `normalize`, and, **for a value physics owns, tells the physics world**: a body's Position or Rotation is read from where it is now, then written and teleported (`setPose`); Friction and Restitution change the surface; Gravity calls `setGravity`; a Hinge's four motor values call `setMotor`. **The Position or Rotation of an entity that isn't a body but has a surface, a body or a joint in it is skipped**, and **a value physics owns that the contract can't change yet** (any BodyComponent field, a joint's other fields) **is skipped with the play warning `valueFixedInPlay`** (standing yes, 2026-11-22). *Why one writer: every changed value has one road, and v5's `set_attribute` will take the same one.*
- **Body › Velocity** (fix 3, replacing Push) goes to the body the target belongs to, its own or the nearest above it, whatever its mass: Set calls `setLinearVelocity(body, v)`, keeping the spin; Add and Subtract call `addVelocity(body, ±v)`. A target with no body is skipped, and a Static body doesn't move.
- **Multiply and Divide** (fix 10) go through `PlayValueWriter` like Add: a number, or each part of a vector, times or divided by the amount; **dividing by 0 leaves the value**. Body › Velocity reads the body's speed now (`velocity(body)`), scales it and sets it with `setLinearVelocity`, keeping the spin.
- **A variable in a value box** (fix 10) is read by `amountNow` as its block runs: the level's on the World, an own one on each target as the action reaches it (`this` for a Wait), so an earlier change in the same run is seen. A target lacking it is skipped; the value check is false there. A Wait's seconds are kept to 0 to 3,600, and a Wait whose variable holds no number is skipped. **Fire custom event's number**, typed or read, goes on each hearer's `TriggerFiring` as `number`, for scripts; no trigger reads it.
- **Flip** (v4) goes through `PlayValueWriter` like Set, so the report, the mirror and `VariableWatch` see it. `PlayValueWriter` writes own variables of any type.
- **A component value in the check** (v4) reads the target's value from the play level with `readableValueOf`, or a body's live value from `velocity(body)`; a target without it is false, and a tagged target passes when any tagged entity does. **A body's TransformComponent position and rotation are read where physics has the body now** (`placementNow`, shared with the teleport in `PlayValueWriter`), since the play copy's TransformComponent keeps the values the run started with. A vector value with no axis, a value that isn't a number, and a check with no amount are false. Speed is `Math.sqrt(x*x + y*y)`, not `Math.hypot`, which browsers may round differently. An own variable check on a tag passes when one tagged entity's does.
- **Destroy** marks the target's subtree, removed by `EndOfTickPhase` with v1's removal, so the actions after it still run. An entity already marked is not marked twice (`RemovalMarks.goes`). It never takes the World or the camera.
- **Win, Lose and Restart** are kept on the run as `ending` (`RunEnding`), the first one in a tick winning; the tick finishes, and `Simulation.runTick` does nothing once `end` is set.

## The report, the mirror and the end

- **`TickReport` gains `changes`**, each changed value as `{ entity, component, values }`, only the keys `PlayValueWriter` wrote, at their latest (`ReportCollector`); **`end`**: `{ kind: 'won' | 'lost', tick }` or `{ kind: 'restart' }`; and **`warnings`**, the `PlayWarning`s first given in the batch (`PlayWarnings.takeNew`), each a kind with its details, once per run. A teleport also sets the pose's snap flag.
- **`PlayMirror` writes the changes into its level** (own variables too, from v4), so a changed colour, a teleport or a switched-off trigger shows, and the Entity inspector (read-only during play) shows the new values.
- **Win or Lose** puts `PlaySession` in `ended` with its `outcome`; the Play bar reads ENDED and **`EndWindow`** (`ui/end-window/`, in the Play bar's floating layer, under it) shows the title and the time, the run's tick count as `m:ss.hh` (`runTimeText`, `editor/play/end/`). Leave is Stop.
- **Play warnings** go to the message pill, which stays on the page during play, written by `playWarningText` (`editor/play/warnings/`), until the Console comes in v5.

## Restart

- **Restart** (the action or the end window's button) starts a new `Simulation` from the `LevelData` and clock time the game worker kept from the last `start`, until a `stop`; a `restart` request is answered like a start (standing yes, 2026-11-22). Nothing is reset in place. `GameRunner` has `restart()`, and `DirectGameRunner` keeps them the same way. `PlaySession` keeps the `LevelData` it sent, so `PlayMirror` starts again from it. One worker does it; the tech notes' spare worker isn't needed, since the level is already read.
- **The last frame stays on screen while the new run starts**, so nothing flashes, and **a paused run restarts paused**. Restart is ignored while a run is starting and once it failed, crashed or hung.
- **The guard against a restart loop:** a Restart action in the first second of a run (ticks 1 to 60) is skipped with the play warning `restartIgnored`, and the rest of the tick runs. *Why: a level-start trigger that restarts would otherwise rebuild the level every tick, the "restart loop that could freeze the computer" the requirement names.*

## Keys during play

- **While the game has the keyboard, `KeyboardInput` prevents the browser's default for every key the level uses**, so Space and the arrows don't scroll, and passes the rest on. It is given `PlaySession` as its `GameKeys`, whose `usesKey` answers from `levelKeys` (the inputs' keys and the triggers' raw keys) while the run plays or is paused. The keys that can't be bound never reach a level.

## Determinism

- **Everything new is ordered**: events in their fixed order, triggers in Entities viewer order, targets with a tag in Entities viewer order, touches by the ids of the two entities. No hash map is walked.
- **`stateHash` adds the World's variables' values after the camera, in list order**, and nothing for a level with none, so the older levels' hashes are unchanged. The three trigger levels and their recorded inputs are in [testing.md](testing.md#the-determinism-test).
- **v4's `stateHash`** (`playNumbers`, `core/simulation/hash/`, after the camera): **a World number is the number alone**, as v3 hashed it; **every other value carries a type mark** (1 number, 2 string, 3 boolean), a boolean as 0 or 1 and a string as its length and UTF-16 code units; **each other entity with a VariablesComponent adds its id and its number of variables** before them, in Entities viewer order, so values can't slide from one entity to the next; **the waiting runs add their count, then each one's due tick and next action index**, and nothing when none wait. A level with no variables on entities other than the World and no waiting runs hashes as before, so the older levels' hashes are unchanged. v4's two levels, `trigger-doors` and `trigger-hits`, are in [testing.md](testing.md#the-determinism-test).
