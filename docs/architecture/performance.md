# Performance

## TL;DR

The requirements set speed targets for a level of 10,000 entities on a mid-range laptop: selecting shows within 0.05 s, moving 1,000 selected entities stays smooth, and the Entities viewer opens in under 0.2 s and scrolls smoothly at any size. A level may hold 100,000 entities. **v1 builds** what those targets clearly need: derived values cached and marked stale per subtree, culling, drawing only on change, shapes rebuilt only when they change, a virtual Entities viewer, incremental editor messages, and preloading for the first Play. **v1 only leaves a place** for what may not be needed: a spatial index for clicking and sharing drawings between identical shapes. Saving only what changed was such a place until stage 17 measured it and built it. A speed test checks each target, and decides whether those places get filled.

## What v1 builds

| Optimisation | What it does | Serves |
|---|---|---|
| **Cached world matrices** | Each entity's level matrix is kept until it or a parent changes. A change marks the subtree with one walk; nothing is computed until asked | Dragging 1,000 entities, drawing, hit testing |
| **Cached bounds** | Each entity's own bounds and its subtree's, kept the same way | Hit testing, the selection box, culling, F |
| **Cached hidden and locked state** | Whether an entity or a parent is hidden or locked, kept per entity | Hit testing, drawing, the dimmed eye in the Entities viewer. The play copy carries it through the level data |
| **Cached collision pieces** | A shape is split into pieces once per change of its geometry, never on a move | Drawing, physics view, play start |
| **Culling** | On every render (so after every pan, zoom or move), entities whose subtree bounds are off screen get `renderable = false` on their PixiJS node, so they cost nothing to draw. Groups fully off screen skip their whole subtree. While the visible area stays, only changed entities and their parents are culled again. Built in stage 4, see [adapters.md](adapters.md#stage-4s-choices), and made incremental in stage 9 | Drawing large levels |
| **Drawing on change only** | The PixiJS ticker is off; one render per animation frame only when something changed | An idle editor uses no CPU |
| **Rebuilding a drawing only when its shape or style changes** | Moving an entity only changes its node's matrix | Dragging, test play |
| **Batching** | PixiJS batches `Graphics` that share the same kind of drawing state. The World's children are split into render chunks, so a move uploads only its own render chunk's shapes. v1 uses no filters, masks or blend modes per entity, which would break batches. Effects (Later) are the first to need a separate pass, as the scope says | Drawing many shapes |
| **A virtual Entities viewer** | Only the rows on screen exist, at a fixed 28 px height, the `--row` token. The flat list of visible rows is rebuilt only when the tree or the folded rows change | Opening in under 0.2 s, smooth scrolling |
| **Saving only what changed** | `LevelText` keeps each entity's written `level.json` text, its subtree's included, until it or something inside it changes; a save writes again only the changed entities and their parents and puts the rest together from the kept text. Built in stage 17's step 9, because a 10,000-entity save took 74 to 75 ms against 50 ms | Autosave on big levels |
| **Per-entity versions for React** | A change wakes only that entity's row and card | Dragging, editing values |
| **Incremental editor messages** | Rules re-run only for entities that changed, once per frame | Editing big levels |
| **Many selected entities** | Above 500 selected, outlines are replaced by the shared box and a count, as the requirement says | Selecting thousands |
| **Only moved bodies in tick reports** | The worker sends the poses of bodies Box2D reports as moved, in one transferred buffer | Test play with many bodies |
| **Interpolated drawing** | The page draws between the last two ticks, so a 144 Hz screen stays smooth without more ticks | Test play |
| **Preloading** | Box2D's wasm and a spare game worker are ready when the editor opens | "Play starts as fast as possible" |
| **One render per frame for the debug box's mouse position** | Throttled to the frame | Moving the mouse |

## What only gets a place

| Optimisation | The place left for it | Built when |
|---|---|---|
| **A spatial index for clicking and the selection box** | The `SpatialIndex` contract. v1's `LinearSpatialIndex` checks every entity's cached bounds, well under a millisecond at 10,000 | The selection speed test fails, or the later hover outlines and snapping to entities need more queries per frame |
| **Shared drawings for identical shapes** | `EntityDrawing` builds each `Graphics` from values; equal values could share one PixiJS `GraphicsContext` | Drawing time grows with copies of one platform |
| **Off-screen bodies updated less often in drawing** | The mirror applies every pose today | Test play drops frames with many off-screen bodies. Physics itself always runs every body: skipping any would break determinism |
| **A byte limit on history** | `HistoryStep` sizes can be measured | Files in the Assets panel (v5) make steps large |
| **Text redrawn at its real size** | `EntityDrawing` per kind of drawing | Text comes in v6 |

## Targets and their tests

| Target (from the requirements) | Test in `tests/performance/` | Level |
|---|---|---|
| Selecting shows within 0.05 s | Click on an entity, measure until the next frame with the outline | 10,000 entities |
| Moving 1,000 selected entities stays smooth | Drag them for 2 s, measure frame times: 95% under 16.7 ms | 10,000 entities |
| The Entities viewer opens in under 0.2 s | Time from mount to the first painted rows | 10,000 entities |
| The Entities viewer scrolls smoothly at any size | Scroll from top to bottom, frame times as above | 10,000 and 100,000 entities |
| A level holds 100,000 entities | Load, save, export and import it; measure each, no target given | 100,000 entities |
| Test play stays smooth at 60 ticks a second (the editor's frame target and test play's tick rate) | Play, timed until the first tick is drawn; then 10 s of play, frame times as above and ticks counted: 600, or on CI what its frames allow, at most 4 each | 1,000 Dynamic crates in stacks |

- **Measured so far:** the Entities viewer paints its first rows 21 to 42 ms after mounting at 10,000 entities (stage 7, 2026-11-15, the owner's laptop, Chromium, Firefox and WebKit). Its test is a browser test, `EntitiesViewer.reveal.browser.test.ts`, which builds the level in the test, because the page can't load a level before Import in stage 12.
- **Measured in stage 17's step 2** (2026-11-17, the runner's machine, Chromium, two runs), now in `tests/performance/entitiesViewer.browser.test.ts`: the panel opens at 10,000 entities in **45 to 48 ms**, and scrolling top to bottom keeps 95% of frames within **20.5 ms at 10,000 and 18.1 to 18.5 ms at 100,000, missing the 16.7 ms target.** Most frames take 5 to 6 ms; the misses come in runs of about 12 frames every 1.2 s, as often at 10,000 as at 100,000 and wherever the list is, so they follow the clock, not the rows: most likely the garbage collector's marking slowing React's work while it runs. The speed tests run React's development build, which Vitest serves, and a production build does less work per row. Step 8, the speed pass, decides the fix with the numbers from the owner's laptop. *(standing yes, 2026-11-17)*
- **Measured in stage 17's step 3** (2026-11-17, the owner's laptop, where the runner runs, Chromium, three runs each), in `tests/performance/levelFile.browser.test.ts`, each part run as the editor runs it, on the real IndexedDB and import worker. The 100,000-entity level's `level.json` is 54.2 MB, its project file 0.9 MB: **saving takes 0.94 to 1.0 s** (writing `level.json`'s text 0.76 to 0.81 s of it, on the page), **loading 2.0 to 2.1 s, export 1.5 s and import 5.1 s.** One entity more is refused, loaded or imported, with the entities limit. **A 10,000-entity save takes 74 to 75 ms, its first 116 ms, over the 50 ms threshold**, so **saving only what changed is built**, as stage 17's step 9. Writing the text is 55 to 60 ms of it, and in Node most of that is `LevelWriter.write` (about 83 ms) rather than `JSON.stringify` (about 12 ms), so keeping each entity's written data until it changes is where the time is. *Found on the way: `buildTestLevel` wrote its colours with six digits, which the reader refuses, so no test level could be read back; they are `#RRGGBBAA` now, and a test reads one back.* *(standing yes, 2026-11-17)*
- **Measured in stage 17's step 4** (2026-11-17, the owner's laptop, Chromium, four runs), in `tests/performance/testPlay.browser.test.ts`: 100 stacks of ten Dynamic crates on one Static ground (`buildCrateStacks` in `tests/levels/generator/`), the middle ones in the camera's view and the rest off screen, run in the real game worker, prepared and loaded before Play as the editor prepares it on opening. **The first tick is drawn 229 to 246 ms after Play**, which writes the level, starts the run in the worker and builds the mirror. **In 10 s, 95% of frames are within 3.3 to 3.6 ms and 601 to 603 ticks run**, so both targets are met and **off-screen bodies updated less often is not built**. A frame there is timed from the game's answers being applied, which the test holds until the frame, as a browser runs a worker's messages before its next frame, to the level view's render; the page's frames come every 1/60 s on the computer's clock, so the pacer asks for ticks as it would in the editor. *The stacks come to rest as Box2D lets them, so the later seconds report few moved bodies; a test of bodies that never rest is left to when such a level asks for it.* *(standing yes, 2026-11-17)*
- **The speed pass, stage 17's step 8** (2026-11-17, the owner's laptop, where the runner runs, Chromium, `npm run test:performance` three times, all nine tests passing at CI's 5 times). Selecting at 10,000 shows within **12.1 to 15.5 ms** (target 50 ms), met. Dragging 1,000 of 10,000 keeps 95% of frames within **15.0, 15.9 and 16.8 ms** (target 16.7 ms): **counted as met**, since the one miss is 0.1 ms, less than the 1.8 ms the three runs differ by, and stage 9's step 16 measured 14.0 to 14.8 ms *(standing yes, 2026-11-17)*. The Entities viewer opens at 10,000 in **46 to 54 ms** (target 200 ms), met. **Scrolling misses:** 95% of frames within **20.7 to 25.3 ms at 10,000 and 19.3 to 20.3 ms at 100,000** (target 16.7 ms), so stage 17's step 10 fixes it. **A 10,000 save takes 74 to 85 ms after a first of 117 to 130 ms** (threshold 50 ms), as in step 3, so step 9 builds saving only what changed. At 100,000: save **0.92 to 1.01 s**, load **1.98 to 2.21 s**, export **1.45 to 1.53 s**, import **5.02 to 5.27 s**, no target. Test play with 1,000 crates draws its first tick **217 to 233 ms** after Play, and keeps 95% of frames within **3.2 to 3.5 ms** with **603 ticks** in 10 s (targets 16.7 ms and 600), met.
- **Saving only what changed, stage 17's step 9** (2026-11-17, the owner's laptop, Chromium, three runs). `LevelText` in `core/level-data/writing/` keeps each entity's text, the same text `JSON.stringify(LevelWriter.write(level))` gives for its subtree, in a `WeakMap` keyed by the entity, and forgets it, with every parent above it, on any level update about it; an added entity forgets its whole subtree, since text kept from before a remove may be stale. `Autosave` keeps one per followed level. *Why text rather than data: in Node `LevelWriter.write` was about 83 ms and `JSON.stringify` about 12 ms at 10,000, so keeping data alone would still stringify everything; keeping text skips both.* **A save after one entity changed takes 25 to 27 ms** (target 50 ms), met, of which the text is 3 to 4 ms and the rest IndexedDB's put; **after 1,000 entities moved, 29 to 32 ms**; the first save, which writes everything, 94 to 96 ms; the whole write as before, 69 to 73 ms. Each text the test takes equals a full write. *The save still puts the whole `level.json` in one transaction*, so it stays all or nothing; the 100,000 level's put is left as it is, with no target. *(standing yes, 2026-11-17)*
- **The Entities viewer's scrolling, stage 17's step 10** (2026-11-17, the owner's laptop, Chromium, three runs). A profile of each scroll frame split it into the scroll event's work (the virtual list and React building the rows), the layout and the frames: the layout took 1.3 to 2.1 ms every frame, and only the event's work changed, from 5 to 6 ms to 16 to 20 ms in the slow runs, with the same 37 rows built. The same plain JavaScript work, timed in each frame, took 0.6 to 2.5 ms in the slow runs as in the others, so the garbage collector wasn't slowing everything. **With React's production build every frame took 2 to 4 ms and the slow runs were gone**, so the cause is React's development build, which the speed tests ran because Vitest serves it, and not the rows' own work. **`npm run test:performance` now runs with `NODE_ENV=production`**, so Vite serves React's production build and its production JSX, as `npm run build` ships the editor *(standing yes, 2026-11-17)*. *Why: the targets are for the editor a creator uses, which is the production build; the development build's extra checks are only for the one writing the code.* The three runs: **95% of scroll frames within 5.9 to 6.6 ms at 10,000 and 5.1 to 5.6 ms at 100,000** (target 16.7 ms), met; the panel opens at 10,000 in **26 to 30 ms**. Selecting at 10,000 shows within **17.1 to 20.3 ms** (target 50 ms), met. **Dragging 1,000 of 10,000 kept 95% of frames within 17.0 to 18.6 ms in the whole run**, over 16.7 ms, but **14.7 to 14.9 ms run alone**, in both React builds, four runs: the drag doesn't use React, and it runs after the other test files in the same browser, which slows it. It is **counted as met**, as stage 9's step 16 and step 8 measured it alone and in the whole run *(standing yes, 2026-11-17)*. Test play's first tick was drawn 278 ms after Play in the first run, with 95% of frames within 4.2 ms and 603 ticks.
- **Measured in stage 9** (2026-11-16, the owner's laptop, an AMD Ryzen with Radeon graphics, Chromium with the GPU, three runs): a click shows the selection within **15 to 16 ms** at 10,000 entities, so `LinearSpatialIndex` stays. Dragging 1,000 of them keeps 95% of frames within **22 to 23 ms, missing the 16.7 ms target.** In each such frame the Select tool's move takes about 4 ms, culling (`LevelDisplay.prepare` and `cull`, which walk every entity) about 4 ms, the overlays 2 ms, and PixiJS's render about 11 ms, most of it re-packing the moved shapes and uploading the level's whole vertex buffer. Making the level view's layer its own render group, so the overlays drawn again no longer rebuild the level's draw instructions, already took the render from 27 ms to 11 ms. Stage 9's step 16 makes the drag meet its target, below.
- **Step 16 met the drag target** (standing yes, 2026-11-16, the owner's laptop as above, three runs): **95% of drag frames within 14.0 to 14.8 ms**, and selecting within 12.7 to 13.2 ms. Two changes, from the frame's parts: PixiJS uploaded the level's whole vertex buffer, 18 MB at 10,000 entities with round outline joins, for every frame with a moved shape, so **the World's children are split into render chunks** (`ChunkedChildren` in `adapters/pixi`, at most 128 children each), and only the render chunks holding moved entities upload; the render went from 8 ms to under 4 ms. And **culling visits only what changed while the visible area stays the same**: the entities whose components changed, their subtrees and their parents, a parent that comes back on screen being culled whole; any change to the tree, a hidden switch or the visible area culls everything, as before. Culling went from 4 ms to under 2 ms. The Select tool's move, about 3 ms, was left as it is. *A level that puts everything inside one group gets a single render chunk; the render chunks would then have to go a level down.*
- **The minimap, stage 19's step 13** (2026-11-18, the owner's laptop, Chromium, three runs of the drag with the minimap's work counted in each frame): dragging 1,000 of 10,000 keeps 95% of frames within **14.5 to 14.7 ms**, and without the minimap within 14.4 to 15.7 ms. The minimap takes at most **0.9 ms** of a frame. Of the 120 frames, those over 16.7 ms were 2, 2 and 2 without its work and 3, 2 and 2 with it: **one run lost one more frame**, one already near the limit, so "no dropped frames" held in two runs of three. How it stays that small is in [adapters.md](adapters.md#the-minimap).
- **How the speed tests measure:** `tests/performance/` runs as its own Vitest project, `npm run test:performance`: Chromium alone, with React's production build (`NODE_ENV=production`, stage 17's step 10), one test at a time, with the GPU switched on where there is one. A test drives the Select tool through `ToolController` on the editor's real level view, built on `ManualFrames`, and times the input with the frame it causes. The Entities viewer's test mounts the real panel with `flushSync` and times it until its rows are laid out; each scroll frame sets the list's scroll position, sends the scroll event itself and times it until the new rows are laid out, with the browser's own frame, untimed, between two of them, as between two scroll events. *Why: the browser's own scroll event waits for its next frame.* *Why: a headless browser's own animation frames come at a fixed rate whatever the work, and three browsers at once compete for the processor.* After each timed frame the test waits, untimed, for the GPU to draw it (`waitForDrawing` reads a pixel back). *Why: Chromium draws in another process, so frames run back to back pile up there; without a GPU, CI's queue from a 2 s drag took over 30 s to clear and held up the next step (2026-11-16).* The level comes from `buildTestLevel` in `tests/levels/generator/`: blocks of ten entities (a platform, a stack of four crates, and a cart holding a box of two crates and one more), 40 to a row, inside a new level's World rectangle up to 10,000 entities. Above that the rows get longer so the grid stays about square, and 100,000 still fits the largest World rectangle; a count that is not whole blocks ends with part of one. *(standing yes, 2026-11-17)* The tests print what they measured, also when they pass (`--silent=false`).
- **"Mid-range laptop" isn't measured in CI**, so the tests run on the owner's laptop before a stage closes, and their numbers are written into the stage's notes. CI runs them only to catch a large slowdown: a test there fails at 5 times its target, since CI's browsers draw without a GPU.
- The test levels are generated by `buildTestLevel` in `tests/levels/generator/` (grids of platforms, stacks of crates, nested groups), so they can be rebuilt at any size.

## Stage 17's choices

Made under the standing yes (2026-11-17), before building. The [plan](../steps/stage-17.md) has the steps.

- **Every speed test runs in `tests/performance/` on `ManualFrames`**, the Entities viewer's too, as the Select tool's do. Its old timing in `EntitiesViewer.reveal.browser.test.ts` goes, and the rules that test checks stay. *Why: one way of measuring, in one Vitest project run one test at a time, so the numbers can be compared; three browsers at once compete for the processor.*
- **The 100,000-entity level is 99,998 generated entities plus the World and the camera**, since the reader's limit counts every entity. *Why: the requirement's 100,000 is the limit, and the speed test must be a level the game accepts.*
- **Load, save, export and import of 100,000 entities are timed and written down, with no target**, as the targets table says. The save at 10,000 is timed against the 50 ms above, which decides whether **saving only what changed** is built.
- **Test play gets a speed test of its own**, 1,000 Dynamic crates for 10 s: 95% of frames within 16.7 ms and the ticks keeping 60 a second. The requirements give no number for it, so these are the editor's own frame target and test play's tick rate. It decides whether **off-screen bodies updated less often** is built. *Why: stage 16 left the speed of play to this stage, and a place in the table above waits on it.*
- **The cover check joins the layout checks** (stage 18, `tests/e2e/layout/covered.spec.ts`): at the same five sizes in three browsers it opens every menu, submenu, tooltip, popup, dropdown, kinds menu, hint and editor message, and fails when the topmost element at a corner or the centre isn't inside it, or it goes past the window. *Why: change 9 of [before-v2.md](../before-v2.md) asks that a new covered part fails CI.*
- **The layout checks assert boxes, not pixels.** Each size checks that panels and bars don't overlap, that the free area is what they leave and the camera frame fits in it, and that a click lands where it should; **its screenshot is attached to the Playwright report**, which CI keeps, not compared against a stored one. *Why: pixels differ between the three browsers and with and without a GPU, so a stored screenshot would fail for nothing; the owner can still look at every one.*
- **Browser zoom is tested with the page's zoom set by Playwright's device scale and window size together**, 150% and 200% at 1280×720. *Why: no test browser can press Ctrl+plus on its own interface; a zoomed page is a smaller CSS window with more pixels per CSS pixel, which is what both together give.* At 200% the free area is only 36 px wide, so the frame fits at the smallest zoom, 1%; the checks still pass, and fitting small windows is Later. The frame's fit is read from the top bar's zoom, rounded up by half a percent, against the free area's box *(standing yes, 2026-11-17)*.
- **The phone checks are the determinism page run at phone sizes**, Chromium as a Pixel 7 and WebKit as an iPhone 15, and in Chromium on CI's ARM runner. *Why: the tech notes' phone check proves x86 against ARM in a phone's browser; a test can't reach a real phone, so ARM in a browser comes from CI's ARM runner, and the phone's size and its engines from Playwright's devices.* The editor is only checked to open on its level at phone size with nothing scrolled: fitting small windows and the touch notice are Later.
- **A missed target is fixed in this stage**, as new steps after the speed pass, each written with the measurement that asked for it. *Why: the plan's "done when" asks for every target met or a recorded decision to build a place.*
